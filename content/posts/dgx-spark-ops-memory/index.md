## Persistent Memory with Letta

### What Letta Is

- Letta provides persistent memory and infinite context for LLM agents
- Instead of stuffing everything into the context window, Letta manages memory as structured data — core memories, archival storage, and conversation history
- Agents can recall information across conversations, update their own memories, and search archival storage via embeddings
- Runs as a server (port 8283) that Open WebUI and other clients can interact with

### The Fork: Streaming + Reasoning Support

- The stock Letta doesn't support streaming with reasoning content — three branches had to be merged:
  1. **`feat/openai-stream-with-reasoning`** — Pluggable output formatters for streaming with reasoning
  2. **`feat/vllm-streaming-support`** — vLLM provider streaming
  3. **`feat/reasoning-content-model-extra`** — Extract `reasoning_content` from `model_extra`
- Fork source: `git@github.com:stevemurr/letta.git`
- Key modifications:
  - `letta/settings.py` — New settings: `openai_stream_include_reasoning`, `openai_stream_output_format`
  - `letta/services/streaming_service.py` — Stream transformers with reasoning and tool call formatting
  - `letta/llm_api/openai_client.py` — OpenAI client modifications for streaming

### Critical Requirement: `stream=true`

- Letta mandates `stream=true` for all chat completion requests
- Non-streaming calls fail with `LettaInvalidArgumentError`
- This is why the LiteLLM streaming patches from Post 2 are essential — without them, reasoning content is lost even though Letta requires streaming

### pgvector for Embedding Storage

```sql
-- init-letta-db.sql
CREATE EXTENSION IF NOT EXISTS vector;
```

- Letta's database runs on PostgreSQL with pgvector 0.5.1
- The `init-letta-db.sql` script enables the `vector` extension on container startup (mounted via `docker-entrypoint-initdb.d`)
- Embeddings are generated by BGE-M3 (the same model serving the rest of the platform) through LiteLLM

### BGE-M3 for Multilingual Embeddings

- BGE-M3 is a multilingual embedding model supporting 100+ languages
- Runs as a dedicated vLLM instance on 10% GPU allocation
- Used by both Letta (memory search) and GPT Researcher (source ranking)
- 8K token max context — sufficient for embedding document chunks

### Letta Environment

```yaml
LETTA_PG_URI: postgresql://letta:letta@letta-db:5432/letta
OPENAI_API_BASE: http://litellm:4000/v1
OPENAI_API_KEY: ${LITELLM_MASTER_KEY}
LETTA_OPENAI_STREAM_INCLUDE_REASONING: "true"
LETTA_OPENAI_STREAM_OUTPUT_FORMAT: openwebui
```

- All LLM calls go through LiteLLM (not directly to vLLM)
- Output format set to `openwebui` — formats reasoning and tool calls for Open WebUI's rendering

## Monitoring the GPU Stack

### Prometheus Scraping vLLM Metrics

```yaml
# monitoring/prometheus.yml
global:
  scrape_interval: 15s
  evaluation_interval: 15s

scrape_configs:
  - job_name: nemotron3
    static_configs:
      - targets: ["nemotron3:8000"]
    metrics_path: /metrics

  - job_name: embeddings
    static_configs:
      - targets: ["embeddings:8000"]
    metrics_path: /metrics
```

- Scrapes vLLM's built-in Prometheus endpoint every 15 seconds
- Two targets: the primary chat model and the embedding model
- vLLM exposes rich metrics out of the box — no extra instrumentation needed

- Grafana runs on port 3000 with persistent storage

### Metrics That Matter Day-to-Day

- **Token throughput** (tokens/sec) — is the model keeping up with requests?
- **Request queue depth** — are requests backing up waiting for a sequence slot?
- **GPU memory utilization** — how close to the allocation limit?
- **KV cache utilization** — are long conversations filling the cache?
- **Time to first token (TTFT)** — user-perceived latency
- **Inter-token latency** — streaming smoothness

## Secure Remote Access

### Tailscale VPN Sidecar

```json
// tailscale/open-webui-serve.json
{
  "TCP": {
    "443": { "HTTPS": true }
  },
  "Web": {
    "${TS_CERT_DOMAIN}:443": {
      "Handlers": {
        "/": { "Proxy": "http://open-webui:8080" }
      }
    }
  }
}
```

- Tailscale runs as a sidecar container (`ts-open-webui`) alongside Open WebUI
- Exposes Open WebUI over HTTPS on the Tailscale network with automatic TLS certificates
- Access from any device on the tailnet — phone, laptop, remote workstation
- **When to use:** Personal/trusted device access, low latency, no public exposure

### Cloudflare Tunnel

- `cloudflared` container creates a tunnel to Cloudflare's edge network
- Exposes Open WebUI on a public domain without opening firewall ports
- **When to use:** Sharing access with others, accessing from networks where Tailscale isn't installed
- Trade-off: adds latency through Cloudflare's edge, but provides DDoS protection and access logging

### When to Use Which

| | Tailscale | Cloudflare Tunnel |
|---|---|---|
| **Access** | Tailnet devices only | Public internet |
| **Latency** | Direct (peer-to-peer) | Through Cloudflare edge |
| **Setup** | Install Tailscale on each device | Share a URL |
| **Security** | Device-level auth | Domain-level auth + WAF |
| **Best for** | Daily personal use | Sharing, demos, mobile fallback |

## Operational Lessons

### Docker Health Checks and Dependency Ordering

- 14 services means startup order matters — models take minutes to load
- Health checks on model servers use HTTP endpoints with generous startup periods (120s for TTS)
- `depends_on` with `condition: service_healthy` ensures downstream services wait:
  - LiteLLM waits for `litellm-db`
  - Letta waits for `letta-db`
  - Open WebUI waits for LiteLLM (its API gateway)
- Without health checks, services would crash-loop during model loading

### GPU Resource Allocation Strategy

<!-- IMAGE: gpu-allocation.png — diagram showing GPU resource split across services -->

| Service | GPU Allocation | Why |
|---|---|---|
| Chat model (Nemotron 3 / GPT-OSS) | 70–75% | Primary workload, needs room for KV cache |
| Embeddings (BGE-M3) | 10% | Small model, low concurrency |
| TTS (Qwen3-TTS) | 5% | Small model, burst usage |
| Whisper | Shared | Uses GPU but doesn't need reserved allocation |

- Total adds up to ~90% — leaves headroom for CUDA overhead and peak loads
- The `model` CLI enforces mutual exclusion for chat models sharing port 8355

### What Breaks, What's Rock Solid

**Rock solid:**
- vLLM serving — once loaded, it just runs
- SearXNG — lightweight, zero maintenance
- Prometheus/Grafana — set and forget
- Tailscale sidecar — auto-reconnects, handles key rotation

**Needs attention:**
- LiteLLM streaming patches — must be re-validated when LiteLLM updates
- Letta fork — three branches to keep merged with upstream changes
- Model loading times — cold start of Nemotron 3 Nano takes a few minutes; swapping models means downtime
- Open WebUI tool import — `gpt_researcher_tool.py` must be manually imported after first deploy

### What I'd Do Differently

- **Pin LiteLLM version** — currently tracking `main-latest`, which means patches can break on any pull
- **Automate tool import** — the manual GPT Researcher tool import step is easy to forget
- **Add alerting** — Prometheus collects metrics but there are no alert rules yet; adding PagerDuty or Slack alerts for queue depth spikes would catch issues faster
